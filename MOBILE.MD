Make the ENTIRE existing application extremely mobile-friendly and fully responsive, with MOBILE-FIRST design as the highest priority. This is a responsive refactoring task, not a redesign of the application's functionality. Preserve all existing features, business logic, API calls, database logic, authentication, calculations, routes, existing data flow, and functionality exactly as they currently work. Do not remove or simplify existing features just to make the UI responsive. First inspect the complete existing frontend codebase, all pages, layouts, reusable components, tables, forms, modals, dialogs, dropdowns, navigation, dashboards, charts, cards, filters, reports, PDF controls, buttons, inputs, and any other UI elements, then systematically make every part responsive.

The application must be designed mobile-first, meaning the base/default layout should work perfectly on small mobile screens first and then progressively enhance for tablets, laptops, and large desktop screens. Do not treat desktop as the primary layout and simply shrink it for mobile. Design every component starting from narrow mobile widths and then add responsive behavior for larger screens. The application must work properly on common mobile widths including approximately 320px, 360px, 375px, 390px, 414px, and 430px without horizontal scrolling or broken layouts. It must also work correctly on tablets, laptops, and large desktop screens.

The most important requirement is that NOTHING should horizontally overflow on mobile. The document must never require horizontal scrolling just to access normal application content. Inspect the entire application for fixed widths, min-width values, oversized elements, hardcoded dimensions, large gaps, excessive padding, long text, tables, buttons, forms, cards, charts, navigation elements, modals, and other components that can cause horizontal overflow. Remove or replace problematic fixed widths wherever appropriate and use responsive width utilities, max-width constraints, flex-wrap, grid layouts, overflow handling, and responsive sizing. Do not blindly add overflow-x-hidden to the body or main container as a solution because that can hide broken layouts instead of fixing them. Fix the actual source of every overflow problem.

Make the sidebar completely mobile-friendly. On desktop keep the existing sidebar behavior and appearance, but on mobile convert it into an appropriate drawer, slide-over menu, or collapsible navigation that does not consume unnecessary screen width. Add a clear mobile menu button if required. The sidebar must open and close smoothly, must not push the page horizontally, must not remain partially visible outside the viewport, and must not prevent the user from interacting with the main content. When the mobile sidebar is open, use an appropriate overlay if necessary and allow it to close naturally. Preserve the existing navigation structure and links.

Make the navbar responsive. Ensure the logo, page title, profile controls, logout controls, notification controls, festival/year selector, and other existing navbar elements do not overlap or overflow on small screens. Hide or collapse secondary controls when necessary while keeping important functionality accessible. Long titles must wrap or truncate intelligently rather than forcing horizontal overflow. Buttons and controls should remain usable with touch input.

Make the dashboard extremely mobile-friendly. Dashboard cards must stack appropriately on small screens instead of becoming tiny or overflowing horizontally. Use responsive grids that change from one column on very small screens to multiple columns on larger screens. Cards must have sensible padding and typography on mobile. Numbers such as total donations, expenses, balance, pending payments, resident counts, external donor totals, registered flats, remaining flats, and other statistics must remain readable without overflowing their containers. Long labels must wrap naturally. Do not force everything into one horizontal row on mobile.

Make all tables mobile-friendly. Tables are one of the highest-priority areas. Do not allow desktop-sized tables to break the mobile layout. For each existing table, inspect whether it can be transformed into a mobile card/list layout. Where a card layout provides a better mobile experience, use a responsive mobile card representation while retaining the normal table layout on tablet/desktop. If a table genuinely requires tabular presentation, implement controlled horizontal scrolling ONLY inside the table container rather than allowing the entire page to overflow. The table container must have a clear maximum width of 100%, and the rest of the page must remain responsive. Important information such as member name, flat number, amount, payment status, date, category, and actions must remain accessible. Do not make table text impossibly small just to force the entire table onto a 320px screen. Action buttons should remain usable and should wrap or collapse into an action menu when necessary.

Make all forms mobile-first. Every form must fit comfortably inside the viewport with no horizontal scrolling. Inputs, selects, textareas, date pickers, number inputs, search fields, checkboxes, radio buttons, file upload controls, and buttons must have appropriate mobile sizing. Use one-column form layouts on small screens and progressively use two-column or multi-column layouts on larger screens. Labels must remain visible and readable. Do not place too many inputs side-by-side on mobile. Ensure input text does not get clipped. Use appropriate input heights and touch-friendly controls. Buttons should generally have a comfortable touch target and should not be tiny. Form action buttons should stack or become full-width where appropriate on mobile.

Make all modal dialogs and dialogs responsive. No modal should be wider than the mobile viewport. On small screens, modals should use nearly the full available width while maintaining safe side margins. Long forms inside modals must scroll vertically within the modal when necessary without causing the underlying page or entire document to overflow horizontally. Modal headers, content, and action buttons must wrap correctly. Buttons should stack on mobile when necessary. Ensure close buttons remain accessible. Do not create modals that extend beyond the top, bottom, left, or right side of the viewport.

Make dropdowns, select menus, popovers, date pickers, command palettes, confirmation dialogs, tooltips, and similar floating UI elements responsive. They must remain inside or intelligently align with the viewport and must not extend beyond the screen. Long dropdown labels should wrap or truncate appropriately. Ensure touch interaction works properly on mobile.

Make all search, filtering, and sorting interfaces responsive. Filter bars that currently appear as a long horizontal row on desktop should stack or become collapsible on mobile. Search inputs should use available width without pushing other controls off-screen. Filters can be placed inside a filter drawer or expandable section on small screens if that provides a better experience. Preserve all existing filtering and sorting functionality.

Make the Donations, Residents/Households, External Donors, Buildings, Wings, Flats, Expenses, Payments, Reports, Ledger, Settings, and every other application page responsive. Do not only fix the dashboard. Every route and every page must be reviewed individually. Pay particular attention to pages containing financial tables, resident information, building/wing/flat information, payment status checkboxes, donation forms, external donor forms, expense forms, analytics, and report controls.

Make the resident/household workflow mobile-friendly. Searchable household selectors must not overflow the viewport. Household cards and resident lists must adapt to mobile widths.

Make the External Donor workflow mobile-friendly. External donor fields such as name, phone, organization, donor type, address, amount, payment method, date, and notes must stack correctly and remain fully accessible on mobile. External donor tables/lists must not cause page-wide horizontal overflow.

Make the payment tracking interface extremely mobile-friendly because it may be used directly from a phone while collecting maintenance/donations. Payment status checkboxes or buttons must have large enough touch targets. Avoid requiring precise taps on tiny controls. If a desktop table is used for payment tracking, create a better mobile representation where each member/payment is displayed as a compact card with the essential information and an obvious paid/unpaid action. Preserve all existing payment functionality.

Make the expense management interface mobile-friendly. Expense forms, category selectors, amount inputs, bill upload controls, expense lists, filters, edit/delete actions, and bill previews must all work properly on mobile. Bill images and previews must never exceed the viewport width.

Make charts and analytics responsive. Charts must automatically resize according to their container and never create horizontal page overflow. Do not use fixed chart widths that exceed mobile screen width. Legends should wrap, move below the chart, or collapse appropriately on small screens. Axis labels must remain readable without forcing the page wider. If a chart cannot remain readable at a very small width, adjust its dimensions, spacing, labels, or presentation rather than allowing overflow.

Make all images, logos, icons, uploaded bill images, profile images, and other media responsive. Images must use max-width constraints and preserve their aspect ratio. Nothing should extend beyond its container. Large images should scale down correctly on mobile.

Make typography responsive. Review all font sizes, headings, labels, table text, buttons, card numbers, descriptions, and navigation text. Do not simply make everything extremely small. Use sensible responsive typography so that content remains readable on mobile. Large headings should scale down appropriately. Long text should wrap instead of overflowing. Avoid unnecessary whitespace and excessive desktop padding on small screens.

Make spacing responsive. Desktop padding, margins, gaps, card spacing, section spacing, and page widths should reduce appropriately on mobile. Avoid large empty areas that make mobile screens unnecessarily long. At the same time, do not make the interface cramped. Maintain a clean visual hierarchy.

Make buttons responsive and touch-friendly. Buttons must not overflow their containers. Button groups should wrap or stack on mobile. Important actions should remain visually obvious. Avoid extremely small icon-only buttons unless the icon is universally understandable and the touch target is sufficiently large. Preserve existing button functionality and styling where possible while adapting dimensions for mobile.

Make the application safe-area friendly where appropriate for modern mobile devices. Avoid positioning critical controls flush against viewport edges. Ensure fixed/sticky bottom or top elements do not cover important content. If the application uses fixed navigation or sticky headers, ensure the content has appropriate spacing so it remains accessible.

Review all fixed and absolute positioning throughout the application. Replace desktop-specific absolute positioning when it causes mobile overlap. Any absolute, fixed, sticky, or transformed element must be tested at narrow widths to ensure it does not cover or push important content outside the viewport.

Review every use of width, min-width, max-width, height, min-height, flex, grid, gap, padding, margin, position, overflow, whitespace, and text wrapping in the frontend. Pay particular attention to hardcoded pixel widths and desktop-oriented min-width values. Replace them with responsive behavior wherever appropriate. Do not remove constraints that are logically necessary; instead make them responsive.

Ensure the main application container always uses the available viewport width correctly. Avoid nested containers that accidentally create extra width. Check for body width, viewport width, scrollbar behavior, padding, borders, transforms, and fixed elements that can cause one or two pixels of unwanted horizontal overflow.

Make scrolling behavior intentional. The overall page should scroll vertically normally on mobile. Only components that genuinely require horizontal scrolling, such as wide data tables, should have their own horizontal scroll container. Do not make the entire application horizontally scrollable.

Make the application keyboard and touch friendly. Inputs must remain usable when the mobile keyboard appears. Important form controls should not be hidden behind the keyboard. Ensure touch targets are large enough and spacing between interactive elements prevents accidental taps.

Ensure responsive behavior works at breakpoints rather than only at one specific mobile width. Test mentally and through the code at 320px, 360px, 375px, 390px, 414px, 430px, 768px, 1024px, 1280px, and larger desktop widths. Do not optimize only for a single device size.

Do not create a separate mobile application or duplicate the entire frontend. Use the existing React components and responsive Tailwind/CSS patterns wherever possible. Reuse components and introduce reusable responsive components or utilities when the same pattern occurs in multiple places. Avoid duplicating markup unnecessarily.

Do not change backend APIs, database schemas, authentication logic, business rules, calculations, or existing functionality unless a frontend change absolutely requires it. This task is primarily a frontend responsive refactoring task.

Do not blindly add overflow-hidden to containers to hide problems. Every overflow issue must be investigated and fixed at its source. After implementation, inspect every page and component for horizontal overflow, clipped text, overlapping elements, inaccessible buttons, oversized tables, broken modals, unreadable charts, and controls extending outside the viewport.
